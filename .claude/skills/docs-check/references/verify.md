# 文書をコードと照合する決まり

docs-check で文書をコードと照合するときの正本。メインで照合するときも、`doc-verifier` が照合するときも、これに従う。

## 先に読むもの

- `docs/README.md` の「ドキュメントの役割分担」: 置き場（screens／features／architecture）と参照方向
- 対象が screens の文書なら `docs/screens/WRITING-GUIDE.md`: 画面仕様の書き方

この 2 つの中身はここに書き写さない。食い違いの判定はこの 2 つを正とする。

## 照合の観点

- コマンド・スクリプトが `package.json` と一致するか。パス・コンポーネント名・IPC チャンネル名・設定キーが実在するか
- 機能・挙動・既定値・表示条件・表示文言が実装と一致するか。廃止された機能が残っていないか。大きな載せ漏れがないか
- 置き場が `docs/README.md` に沿うか（参照方向の違反と見出し番号のずれはスクリプトの G・H で見つかるので、照合で重ねて探さなくてよい）
- 画面仕様が `WRITING-GUIDE.md` に沿うか。特に「コード上の名前を本文に書かない」「コードの写しを書かない」
- コードの写し（チャンネル・型・変数・props の網羅表）を増やしていないか。コードを正としてリンクする（`docs/architecture/ipc-channels.md` の冒頭が例）

カテゴリごとの主な照合先: setup は `package.json`・環境変数・設定ファイル、screens は画面のコンポーネント、features はサービス・IPC ハンドラ、architecture はデータ形式・型・ディレクトリ構成、testing はテストの設定とファイル。

## 分類と、直す範囲ごとの扱い

| 区分                           | 例                                                                                                                                                                       | 報告だけ | fix  | fix-all |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- | ---- | ------- |
| 機械的（正解が 1 つ）          | リンク切れ、アンカーのずれ、目次の漏れ、改名されたパス                                                                                                                   | 報告     | 直す | 直す    |
| 食い違い（コードで裏が取れた） | 文言・既定値・表示条件・必須条件の誤り、消えた機能の記述。WRITING-GUIDE への違反のうち、意味を変えずに直せるもの（本文のコード上の名前を言葉にする、コードの写しを消す） | 報告     | 報告 | 直す    |
| 判断が要る                     | 画面一覧への追加、仕様書の新設、節の構成変更、文書の統合・縮小                                                                                                           | 提案     | 提案 | 提案    |

照合の途中で見つけた次の 2 つは、どの直す範囲でも直さずに報告する。

- **コード側の不具合の疑い**: docs ではなくコードが誤っていそうなもの
- **未確認**: コードで裏が取れなかったもの

## 直すときの決まり

- 推測で書かない。直す内容は必ずコードで確かめ、根拠を `ファイル:行` で残す
- 部分的に直す。表の多い文書をまるごと書き直さない（差分が読めなくなる）。直した文書には `npx prettier --write` をかける（表の桁揃えで差分が増えるのは許す）
- 見出しや章番号を変えたら、その見出しを指すアンカー（`grep -rn "<ファイル名>#" docs .claude README.md CLAUDE.md`）を一緒に直す
- 公開リポジトリなので、特定の個人の環境（ローカルのパス・常駐のさせ方など）は書かない

## 1 文書の報告の型

各区分の中は重要度順に並べる（誤ったコマンド・パス・API 名、存在しない機能の記述、参照方向の違反、壊れたリンクを先に）。該当がない区分は「なし」と書く。

```
## <文書のパス>（直す範囲: fix-all）

### 直したもの
- <見出し or 行>: <何をどう直したか>（根拠: src/...:行）

### 直していない食い違い
- <場所>: <docs の記述> と <実装>（根拠）。直さなかった理由。正解が 1 つなら置き換え後の文

### 提案（判断が要る）
- <場所>: <内容と案>

### コード側の不具合の疑い
- <内容>（根拠）

### 未確認
- <場所>: <確かめられなかったこと>
```

`報告だけ` のときは「直したもの」を省く。
