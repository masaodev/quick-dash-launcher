# docs-check — ドキュメントの点検と修正

docs の整備状況を点検する。機械的に判定できるものはスクリプト（`scripts/docs_check.py`）で見つける。コードとの照合は、対象が数本ならメインで直接行い、多いときは `doc-verifier` サブエージェントに 1 文書ずつ渡して、照合から修正まで任せる。

docs の決まりの正本は `docs/README.md`（体系・参照方向）と `docs/screens/WRITING-GUIDE.md`（画面仕様の書き方）。照合の観点・分類・直す決まり・1 文書の報告の型は `references/verify.md` にまとめてあり、メインで照合するときも `doc-verifier` もこれに従う。

## 引数

3 つの軸を組み合わせる。順番は問わない。日本語の言い方も同じ意味に受け取る。

| 軸       | 指定                                                         | 意味                                                                                                                   |
| -------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 深さ     | `quick`（「軽く」「構造だけ」）                              | スクリプトの A〜D・F だけ。コードとの照合はしない                                                                      |
|          | （既定）                                                     | quick に加え、前回の点検以降に変わったコードに関わる文書を照合する（E）                                                |
|          | `full`（「全部」「しっかり」）                               | 既定に加え、全文書をコードと照合する                                                                                   |
| 直す範囲 | （既定）（「見るだけ」）                                     | 直さずに報告だけ                                                                                                       |
|          | `fix`（「直して」）                                          | 正解が 1 つに決まるものだけ直す: リンク切れ、アンカーのずれ、目次の漏れ、実在しないパスの書き換え先が 1 つに決まるもの |
|          | `fix-all`（「全部直して」）                                  | コードで裏を取れた食い違いも直す。節の新設・構成の変更・仕様書の新規作成は提案にとどめる                               |
| 対象     | パス（例 `docs/screens/`、`docs/screens/register-modal.md`） | そのフォルダ・ファイルだけを点検する                                                                                   |
|          | `since=<タグかコミット>`（例 `since=v0.8.0`）                | E の起点を指定する。省略時は `docs/.docs-check.json` の前回の点検                                                      |

例:

```
/docs-check                    # いつもの点検（報告だけ）
/docs-check quick fix          # 構造だけ見て、機械的な誤りは直す
/docs-check full               # 全文書をコードと照合（報告だけ）
/docs-check docs/screens/ fix-all
/docs-check since=v0.8.0 fix
```

始めに「深さ・直す範囲・対象」を 1 行で宣言してから進める。

## 手順

### 1. スクリプトで機械的な点検をする

リポジトリのルートで実行する（Windows では文字化けを避けるため `PYTHONIOENCODING=utf-8` を付ける）。

```bash
PYTHONIOENCODING=utf-8 python .claude/skills/docs-check/scripts/docs_check.py [--since <REF>] [--path <PATH>]
```

| 節                  | 見るもの                                                                                                        | 直し方の目安                                                                                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. リンクとアンカー | 相対リンクの実在、`#アンカー` と見出しの一致                                                                    | 移動・改名先が 1 つに決まれば直す（fix）。決まらなければ報告                                                                                                        |
| B. 目次             | 各フォルダに README.md があり、同じフォルダの .md を全部載せているか                                            | 漏れた文書を、その文書の題と 1 行の説明で目次に足す（fix）                                                                                                          |
| C. 画面の網羅       | 画面系コンポーネント（`*Modal`・`*Page`・`*Dialog`）、`*WindowManager.ts`、直下の `*.html` が docs に出てくるか | `docs/screens/README.md` の画面一覧に載せるか、仕様書を書くかは判断が要るので提案（どの fix 段階でも直さない）。画面一覧に「なし」で行を足すだけなら fix-all で行う |
| D. コードへの参照   | docs の `src/...` などのパス、`npm run X` の実在                                                                | 新しいパスが 1 つに決まれば直す（fix）。機能ごと消えていれば記述の見直しを提案                                                                                      |
| E. 前回以降の変更   | 起点から変わったコードと、そのファイル名に触れている文書                                                        | 手順 2 で照合する                                                                                                                                                   |
| F. 長い文書         | 800 行以上の文書                                                                                                | 情報。急に伸びた文書は、コードの写し（網羅表・型の写し）が増えていないかを手順 3 で見る                                                                             |

### 2. 変わったコードに関わる文書を照合する（既定・full）

E に並んだ「コード → 文書」の組ごとに、変更点に関わる記述が実装と合っているかを照合する。誰が照合するかは文書の数で決める。

| 照合する文書 | やり方                                                                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3 本以下     | メインで `references/verify.md` を読んで直接照合し、直す。サブエージェントは使わない（起動の待ちと報告の中継のほうが重い）                            |
| 4 本以上     | 手順 3 の渡し方で `doc-verifier` に 1 文書ずつ渡す。重点として、その文書に関わる変更コードのパスと `git diff <起点>..HEAD -- <コード>` の要点を添える |

- 文書が多いときは、変更の大きいコードに関わるものから順に
- 「触れている文書なし」のコードは、新しい機能や画面なら docs への追記を提案する（内部の小さな変更なら不要）

### 3. 全文書を照合する（full）

全文書を `doc-verifier` で照合し、直す範囲に応じてその場で直させる。照合と修正を別のエージェントに分けない（同じコードを 2 回読むことになる）。

1. 途中で止まっても再開できるよう、作業用のチェックリストを使う。ルートの `doc-review-checklist.md` があれば、未チェック（`- [ ]`）の文書から再開する。なければ `docs/**/*.md`（`docs/screens/WRITING-GUIDE.md` は除く）をフォルダごとに並べて作る
2. `doc-verifier` に渡す
   - 1 回の起動で 1 文書。150 行未満の小さい文書は、同じフォルダの 3 本までまとめて渡してよい
   - 同時に動かすのは 8 体程度まで。同じ文書を 2 体に渡さない
   - プロンプトには、対象の文書、直す範囲（`報告だけ`／`fix`／`fix-all`）、重点（あれば）だけを書く。観点・直す決まり・報告の型は `references/verify.md` にあり、`doc-verifier` が自分で読むので繰り返さない
3. 報告が届くたびに、チェックリストのその行を `- [x]` にする。報告の「直していない食い違い」「提案」「コード側の不具合の疑い」「未確認」は、チェックリストの下にまとめて控え、手順 6 の報告に使う
4. 直したものは、`git diff -w <文書>` で疑わしい箇所だけ見る（エージェントがコードで裏を取っているので、全部を読み直さない）
5. 全部終わったらチェックリストは削除する（コミットしない）

### 4. もう一度スクリプトを回す

直したあとは `npx prettier --check "docs/**/*.md"` と手順 1 のスクリプトを再実行し、A・B・D が残っていないか（残すなら理由）を確かめる。

### 5. 前回の点検として記録する（既定・full）

E の照合まで終えたら `--record` を付けて実行し、`docs/.docs-check.json` に HEAD を記録する。次回の既定の点検はここを起点にする。記録ファイルは修正と一緒にコミットする。quick のときは記録しない。

```bash
PYTHONIOENCODING=utf-8 python .claude/skills/docs-check/scripts/docs_check.py --record
```

### 6. 報告する

区分は `references/verify.md` の 1 文書の報告の型と同じにする。各区分の中は重要度順。

```
## docs-check の結果（深さ: 既定／直す範囲: fix／対象: 全体／起点: v0.8.0）

| 区分 | 件数 | 直した | 残り |
| --- | --- | --- | --- |
| 機械的 | 3 | 3 | 0 |
| 食い違い | 5 | 0 | 5 |
| 判断が要る（提案） | 2 | — | 2 |
| コード側の不具合の疑い | 1 | — | 1 |
| 未確認 | 1 | — | 1 |

### 直したもの
- docs/screens/main-window.md: アンカー `#428-…` を見出しに合わせた
### 直していない食い違い
- docs/screens/register-modal.md 4.7: 必須条件が実装と違う（useRegisterForm.ts 303 行で確認）
### 提案
- MemoViewModal に画面仕様がない。メモ表示モーダルとして画面一覧に載せ、context-menu.md の節を指す案
### コード側の不具合の疑い
- …
### 未確認
- …
```

コミットと PR はこのスキルでは行わない。CLAUDE.md の「コミット・PR」に従う。
